# UX-01.R1 — Canonical CAD workspace composition and visual conformance contract

Status: **DOCUMENTARY DESIGN CONTRACT — READY FOR OWNER REVIEW** (2026-10-21). This document specifies future visual acceptance; it does not amend frozen UX-01, authorize UX-02, or supersede an ADR. The UI/UX v0.3 package remains **PROPOSED — DESIGN REFERENCE**. Where an image depicts unimplemented CAD behavior, the executable contract remains the accepted product and architecture scope.

## 1. Purpose, authority and evidence

The aim is a readable, coherent, viewport-first personal CAD interface in which the user can find a command, understand the active mode, select the intended object and complete or cancel an edit without internal IDs. This contract interprets the four [registered design images](uiux_v03_pkg/VISUAL_REFERENCE_REGISTRY_V0_3.md) for future bounded campaigns. It preserves the mouse-first editor, FeatureModel ownership, derived presentation, native `.microsw` document, Dear ImGui/GLFW/OpenGL stack and [dependency policy](DEPENDENCY_POLICY.md). A visual treatment must never introduce a new authoritative CAD object, mutate a document merely to display properties, or turn a mockup label into an enabled feature.

Evidence levels are deliberately distinct:

- **D — direct design observation:** the four original PNGs below were opened and visually inspected. Their SHA-256 values match the registry. The PNGs are design intent, not runtime evidence or image assets for the product.
- **E — direct executable observation:** [before](ux01_validation/UX-01-MODEL-BEFORE-CORRECTION.png) and [after](ux01_validation/UX-01-MODEL-EXECUTABLE.png) owner-provided Model captures were opened. The after capture is 1919×1041 pixels; Windows scale was estimated by the owner at 100%, not measured. There is no comparable Sketch executable capture.
- **F — functional evidence:** [UX-01 validation](UX_01_CAD_WORKSPACE_VALIDATION.md), [SET-01 validation](PERSONAL_SOLIDWORKS_SET_01_VALIDATION.md), and `ApplicationShell.cpp` / `FeatureTreeModel.cpp` establish implemented behavior that may be off-screen in E. The owner accepted the 26-step UX-01 gate **WITH CHANGES**; final V3 was 928/928. This is not proof of pixel-level conformance or 125%/150% visual behavior.

All regions share a coherent dark surface hierarchy and keep controls for the active mode discoverable. The native window frame may supply system actions without recreating them in ImGui.

### Proportion and scaling rules

The four 1586×992 design images put E and G at roughly 20% each and F around 60% of the content width (boundaries vary slightly in Export/Manufacture). Their header/menu/tabs/ribbon stack occupies roughly the top fifth, and H roughly the bottom 5%. These are **image observations**, not pixel-perfect instructions. E after correction uses 330 px side panels on a 1919 px capture (about 17% each), yielding about 66% center width; its top shell is about 190 px and status about 52 px. The smaller visible part in E also reflects camera framing, not merely panel allocation.

P: for 1920×1080 at 100%, simultaneously show both panels and a dominant viewport, with at least one unoccluded primary action in each active inspector. At 1366×768, retain mode, current tool, tree, one full-width inspector field and usable viewport; move low-priority ribbon groups to explicit overflow before clipping. During free resize, recompute panel limits and scroll contents rather than letting buttons overlap or disappear. At Windows 125% and 150%, use logical sizing plus DPI-aware font/icon scaling and verify actual screenshots and pointer hit targets. These targets are **proposed**, since the UX-01 validation measured logical layout only and has no owner 125%/150% visual evidence. P tolerance for desktop review: side panel shares may vary by about ±3 percentage points from the reference if F stays useful; header/ribbon can differ by about ±20% height if hierarchy remains legible. Record the achieved widths and whether wrapping/scrolling occurred during future gates.

## 4. Header, workspace taxonomy and ribbon

The executable product name remains Micro SolidWorks / Personal SolidWorks; do not copy “Micro CAD” branding, the `.mcad` example, commercial icons or exact mockup chrome. Show the active `.microsw` basename and dirty cue consistently with the native title and save dialogs. Global search is a **reserved location**, not an active fake field. File/Edit/View/Help and their native-like actions remain authoritative; menu order can differ from D when needed for platform behavior. Primary header text should be more prominent than metadata; dirty state must have a textual or glyph cue with a tooltip.

Conceptual taxonomy: **Model, Sketch, Features, Surfaces, Assembly, Manufacture, Drawing**; Export is a task surface shown only when a future campaign authorizes it. Today Model and active Sketch are functional contexts; Features is an existing family of commands/history inside Model, not a separate complete workspace. Surfaces/Assembly/Manufacture/Drawing are future. UX-REF-04's Export tab does not require a new tab in the current executable. If tabs are later displayed, only real navigable destinations may look enabled. Sketch entry still follows valid plane/face/existing Sketch selection, and Exit returns to Model with clear state.

P ribbon grouping for existing scope: **Document** (New/Open/Save/Save As), **History** (Undo/Redo/Rebuild), **Sketch** (enter/exit; Select/Line/Rectangle/Circle; available relations/dimension), **Features** (Extrude/Cut Extrude), **View** (views/display) and **Exchange** (Export STL). Group order should follow workflow, not a wholesale import of all D icons. Keep global commands locatable across modes; if temporarily unavailable, render disabled with a human reason in tooltip. Active tools get a filled/outlined state and text label; separators signal actual groups. Tooltips state both action and prerequisite. The command sequence, selection requirement and validation feedback must match the Inspector; the ribbon never starts a competing edit transaction.

## 5. Model Browser contract

D's visual tree suggests **Part/Document → Solid Bodies, Origin/Reference Geometry, Sketches, Features**. This is a *presentation grouping*, not new domain ownership. E currently shows Part, Reference Geometry and ordered feature history with absorbed sketches nested beneath their owning features. Preserve that history order, nesting, principal planes, stable logical selection and existing right-click, F2, Delete, show/hide, editing and FAILED/BLOCKED cues. A future “Sketches” visual category must not duplicate absorbed nodes or give one Sketch two editable locations. A “Solid Bodies” view, if ever authorized, must derive labels from current feature results and must not invent persistent BodyIds.

P row geometry: single readable line of text with icon inside the row, at least ~24 logical px row height at 100%, 12–16 px icon, 16–20 px indentation per level and a separate disclosure affordance. These numbers are design targets pending real DPI review. A row must never draw its icon over a neighbor or clip the selected label. Use project-owned icons with a consistent optical center; preserve a reserved trailing slot for visibility/error state. Hover gives a subtle row background and tooltip with full name/type/state; selected gives a stronger SET-01 accent and remains recognizable when the viewport has focus. FAILED and BLOCKED show distinct symbols and a readable diagnostic; hidden/dirty/editing have distinct labels/tooltips. Do not rely on color alone.

Naming is human-readable and editable through current Rename/F2, with duplicate/empty-name validation. Search is a **future UI affordance**: when authorized, filter or reveal existing nodes without reordering FeatureModel history, changing selection or editing IDs. Right-click actions are context-specific and disabled with reasons where appropriate. Tree selection and viewport logical selection converge on the same object; transient face/edge selection may reveal the owning feature without falsely promising persistent topological naming. When a dependency is selected, the Inspector can explain its impact without mutating the document.

## 6. Context Inspector / PropertyManager contract

The Inspector is a **contextual work surface**, never a developer dashboard. Its input tuple is current workspace + active command + active feature + logical selection + edit draft + validation state. A selection change may replace read-only content but must not silently commit a draft. One active edit has one owner and one final-action area. P internal order: context header/name/type; relevant selection/source/target; parameter sections; units and validation; preview/feedback; pinned or consistently positioned **Confirm** and **Cancel**. Only show tabs when they separate real content; do not reproduce empty “Advanced” tabs. Fields have descriptive labels, explicit mm/degrees/other units, range/help, numeric precision appropriate to the domain and inline error near the field. Preview state is clearly provisional. Diagnosis includes what failed and a recovery action, with technical IDs only in optional diagnostics.

| State | Required visible content and behavior |
| --- | --- |
| **Idle / no selection** | Brief next-step guidance relevant to Model/Sketch; no generic Sketch solver controls in Model. Avoid filling empty space with developer telemetry. |
| **Feature selected** | Name/type, source Sketch/target when relevant, committed parameters, dependencies, state and valid Edit/Rename/Show/Hide/Delete actions. Merely opening this view leaves dirty/Undo unchanged. |
| **Face or edge selected** | Face/edge type and owning feature, supported contextual action with reason when unavailable; distinguish transient sub-element from feature identity. |
| **Sketch editing** | Current Sketch and tool, selected entity, geometric values/dimensions/constraints/solver status, scope of Apply or Solve and clear Exit Sketch. Avoid two simultaneous authoritative radius controls. |
| **Feature editing** | Draft source/target/depth/direction and preview/validation; Confirm commits once and Cancel discards all draft changes. Keep final actions visible and in a stable order, even while scrolling. |
| **FAILED / BLOCKED** | Plain-language failing feature/upstream cause, last-known-good versus proposed result, actionable recovery/rebuild path; avoid success coloring on an invalid state. |

F confirms much of the state logic already exists in `ApplicationShell.cpp`; the new work is presentation and consistency, not an instruction to rewrite FeatureModel. Reading properties/diagnostics is side-effect-free. A cancelled operation must preserve authoritative geometry, dirty state and Undo/Redo. Invalid input must retain the editable draft and show why Confirm is unavailable. A successful operation must leave a stable post-command mode rather than a stale input form.

## 7. Graphics Area and viewport HUD

F is the primary work surface. Preserve CAD-authoritative geometry and derived tessellation/presentation. The present **Shaded**, **Shaded With Edges** and **Wireframe** modes remain distinct; cosmetics must not change kernel or CAD tessellation semantics. Use background/grid contrast that supports geometry, not a grid so strong that it competes with the part. In Sketch, show a plane-normal orthographic canvas with visible X/Y and meaningful snap/inference markers. In Model, preserve readable silhouette, hover pre-highlight and selected emphasis, including faces/edges. SET-01 Orange/Blue affects selected state only; hovered remains visually distinct. Apply any blueprint-like edge/annotation styling only to derived overlays.

For D's stronger visual framing, propose a predictable Fit command plus an appropriate initial camera framing; no automatic camera motion while editing a field. Dimension callouts, selected-edge annotations and preview outlines should be spatially tied to geometry, update with camera/projected positions, and avoid obscuring the pick target. The current preview/snap/inference overlays are a foundation. Future **DimensionCallout**, constraint indicator, selected handle, context micro-toolbar, preview line and validation badge form a consistent visual language: same font hierarchy, selection color, restrained leader line and explicit provisional/error state. A visual contract alone does not authorize new solver semantics, draggable constraints, handles that modify geometry or other advanced manipulation.

Existing HUD: Fit, ISO, standard views through Views/Space, display menu and X/Y/Z cues (F). P placement: keep a compact view cluster at an upper viewport corner, a persistent orientation cue/triad away from the model and unobstructed picking, with tooltips and keyboard equivalence where already supported. Show the active projection/display mode where needed to interpret the scene. Respect SET-01 Profile A default (**MMB Orbit; Shift+MMB Pan; wheel Zoom**) and optional Profile B swap; no surprise change to orbit direction or gesture contract. D's interactive View Cube is **DEFERRED** and must not be represented by a dead clickable cube. If later authorized, it must call real standard-view operations and be tested in perspective/orthographic views.

## 8. Design system and accessibility

**Typography.** Preserve the UX-01 installed Windows UI font correction and fallback. P 100% targets: body/field labels ~14–17 logical px, panel headings ~16–20, caption/secondary text no smaller than ~12–13; values and units must share a clear baseline. Use regular/medium weight for hierarchy before excessive color. Align numeric columns and decimal precision; keep tooltip text readable rather than tiny pixel type. Test actual glyph rasterization at 100/125/150% and fallback font, not merely window geometry.

**Iconography.** Use original project-drawn or expressly licensed resources, never extracted proprietary artwork. P ribbon icon ~24–32 logical px with a short visible label; Browser/HUD icons ~14–20; consistent stroke weight, optical alignment, inset and hover/focus bounds. Filled/outlined variations communicate active state; disabled state retains recognizable shape and readable reason. Labels must survive icon ambiguity. No overlap, truncated text without tooltip, or incongruent icon scales across regions.

**Semantic tokens.** The palette should name roles rather than bake one blue into all states: `Background`, `Panel`, `Viewport`, `Text Primary`, `Text Secondary`, `Selected`, `Hovered`, `Active`, `Success`, `Warning`, `Error`, `Disabled`. D supplies graphite surfaces and blue active-tool accents. **SET-01 overrides selection:** Orange is the default selected geometry/tree accent, Blue opt-in; Profile A is the default navigation mapping, Profile B opt-in. Neither changes Hovered, Warning or Error. Selected versus hovered must remain distinguishable under both accents and all three display modes. Error/warning/success carry a word or symbol in addition to color.

**Accessibility acceptance.** At future implementation gates, inspect text/controls at 1366×768 and 1920×1080, plus Windows 100/125/150% where available; verify no clipped controls, sufficient contrast by measured foreground/background pairs, discoverable focus indication, tooltip for icon-only controls, keyboard path to primary menu/actions and mouse targets large enough for reliable selection. P minimum hit target ~28 logical px for compact toolbar/tree actions, larger for primary ribbon buttons. Verify active, disabled and focused states in both accent options. Do not claim WCAG or other formal compliance without a dedicated measured audit. A missing scale environment is `NOT VERIFIED`, not PASS.

## 9. Model, Sketch, Export and Manufacture coherence

Model and Sketch reuse the same A/B/E/F/G/H positions so entering Sketch does not make the Browser disappear or move the Inspector. Model uses shaded 3D context and feature commands; Sketch changes D to drawing/dimension/constraint commands, F to normal-to-plane canvas with X/Y, G to sketch entity/constraint context, H to the next pick/edit step, and offers an unmistakable Exit Sketch. Dimension values must remain synchronized with solved geometry and invalid constraints must be diagnosed. UX-REF-02's on-canvas editable dimensions and local toolbar are UX-02 candidates, not claims about UX-01. A Sketch executable capture should be acquired at UX-02's visual gate; the owner UX-01 review is functional/visual observation without an archived Sketch image.

UX-REF-04 extends the shell to a future Export task, but frozen v1.2.0 already provides File → Export STL with body/quality/destination and real mesh validation. A richer checklist must reflect validator output; a blue mesh preview must be derived from the same export candidate, not a cosmetic image. Other formats, import, repair, split CAD/mesh comparison and an Export tab remain outside present authorization. UX-REF-03 demonstrates future product coherence only. It does **not** authorize stock, CAM operations, toolpaths, simulation, post-processing or G-code. No fake Manufacture surface should appear functional.

## 10. Interaction contract and visual acceptance

For each existing command: **invoke → explain eligible selection → collect selection → show a truthful preview/draft if supported → validate → Confirm or Cancel → stable result**. The Browser, viewport, ribbon and Inspector share one editor state. Hover shows the next pick; selection persists until the tool semantics change it; unavailable commands explain their prerequisite. Context right-click exposes only actions valid for the current target. Esc cancels a transient drawing step or edit at the appropriate level without changing committed CAD state. Normal work requires labels and CAD concepts, not internal IDs. Dirty/Undo/Redo and save/exit behavior remain governed by the existing document session.

Future visual acceptance should capture at least Model idle, feature selected, face selected, feature edit draft, Sketch editing with selected entity/dimension, FAILED/BLOCKED if safely reproducible, and STL dialog. Compare each to the relevant D image for *composition and hierarchy*, not pixel identity or unimplemented commands. At 1920×1080 and 1366×768 verify A–H visibility, F dominance, panel min widths, group/field legibility, nonoverlapping icons, clear active workspace and accessible final actions. Repeat at 125/150% when available; record omissions. Walk through create/edit/cancel/confirm/Undo/Redo/save/open using only named UI actions. Check both SET-01 selection accents and navigation profiles without changing their defaults. Report deviations with screenshot, resolution, DPI, state, expected contract and observed behavior; do not infer functionality from a static image alone.

## 11. Deferred scope, campaign mapping and UX-02 handoff

**UX-02 — Guided Sketch interaction** is the next *candidate*, **NOT STARTED**. Mandatory visual contracts to carry into its proposal: same shell across Model/Sketch; explicit mode/Exit; normal-to-plane grid and X/Y; clear selected entity and active tool; readable dimension callouts grounded in real constraints; synchronized Inspector values/solver diagnostics; honest preview and Confirm/Cancel; no regression to Browser visibility, feature ownership, document safety or SET-01 preferences. Existing functional dependencies include Line/Rectangle/Circle, sketch plane/face support, solver, dimension application, preview/snap/inference, selected logical target, Undo/Redo, feature rebuild and viewport projection. The UX-02 implementation must specify exactly which callouts/direct edits and local toolbar actions are supported; appearance-only placeholders do not satisfy it. Test mouse-first creation, dimension edit, invalid input recovery, cancel and solved geometry change with relevant screenshots and a focused Experience Gate.

Remaining future gaps: full Browser search/body grouping, interactive View Cube, richer Model Inspector/ribbon treatment, Export workspace/split preview, and all Manufacture concepts. Hole Wizard, Fillet, Chamfer, Revolve, STEP, assemblies, scripting, persistent topological naming, kernel replacement and advanced manipulators are not authorized by these images. Model Workspace Refinement is a sensible later candidate but **has no new campaign number yet**. The current [roadmap](ROADMAP.md) already uses **UX-03 for Export UX** and **UX-04 for future workspaces**, whereas the R1 prompt suggests UX-03 Model refinement and UX-04 Export Experience. Keep existing identifiers until the owner explicitly resolves numbering and scope. The order can be reviewed after UX-02 without retroactively renaming a planned campaign.

Owner review questions: confirm proposed desktop/DPI metrics and whether grouping the Browser by bodies/sketches would improve clarity while preserving absorbed-sketch history; decide when command search and View Cube merit implementation; reconcile the future campaign numbering. None blocks this *documentary* contract, and none changes an accepted architectural decision.
